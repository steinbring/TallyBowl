# TallyBowl — Platform & Code Audit

- **Date:** 2026-10-23
- **Scope:** Full Flutter source (`lib/`), native bridges (`android/`, `ios/`, `macos/`), build configuration, and packaging metadata.
- **Targets in scope:** Android, iPadOS, macOS. (Web/Windows/Linux are out of scope.)
- **Purpose:** Identify issues — security, compatibility, accessibility, cohesiveness, and maintainability — that must or should be addressed before the app is usable/releasable on the three target platforms.

This document is written to be consumed by a follow-up AI or engineer. Each finding includes a stable ID, severity, affected platform, file reference, and a concrete recommendation.

Severity legend:

- **P0 — Blocker:** prevents the app from building, launching, or being distributed on a target platform.
- **P1 — High:** a real defect or release-blocking gap that will affect most users.
- **P2 — Medium:** correctness/UX risk that should be fixed before a polished release.
- **P3 — Low:** hygiene, polish, or future-proofing.

---

## 1. Executive summary

The Dart layer is well-structured and the persistence, scoring, and export logic are unusually careful (transactional snapshots, validation, CSV formula protection, bounded network parsing). The biggest risks are in the **native/platform boundary** and in **packaging/distribution**, not in the core domain logic.

Highest-priority items to fix before treating this as usable on all three platforms:

1. **Android release is signed with debug keys** (P0 for distribution).
2. **Android camera path has no explicit `CAMERA` permission and uses a raw `file://` URI with ML Kit** (P1; camera flow is compile-verified only).
3. **Android physical-device camera/recognition/share flows are untested** (P1; documented as such, but still a release blocker).
4. **Development map/search services (public OSM tiles + Photon demo) are still the defaults** (P1; usage policies and availability are not production-grade).
5. **No large-text accessibility testing and several hardcoded tiny font sizes / no dark theme** (P2, all platforms; iOS review and real-world accessibility).
6. **macOS distribution signing/hardened-runtime/notarization is not configured** (P1 for App Store / notarized distribution).

The remainder of this document itemizes these and lower-severity findings with references.

## 3. Security

### SEC-01 — Android release signed with debug keys — P0
- **File:** `android/app/build.gradle.kts`
- **Evidence:**
  ```kotlin
  buildTypes {
      release {
          // TODO: Add your own signing config for the release build.
          signingConfig = signingConfigs.getByName("debug")
      }
  }
  ```
- **Impact:** A release APK/AAB is signed with the well-known public debug key. It cannot be published to Google Play and is trivial to impersonate.
- **Recommendation:** Create a real upload keystore and wire `signingConfigs.release` (ideally via `key.properties`/environment variables, kept out of version control). Use Play App Signing for the AAB path.

### SEC-02 — Android camera permission not explicitly declared — P1
- **File:** `android/app/src/main/AndroidManifest.xml`
- **Evidence:** Only `android.permission.INTERNET` is declared in the main manifest. Camera access is used via `image_picker` (`lib/src/recognition/photo_service.dart`, `ImagePicker().pickImage(source: ImageSource.camera, ...)`).
- **Impact:** The `image_picker` plugin normally declares `CAMERA` in its own manifest and relies on manifest merger. This generally works, but it is implicit, easy to break during a plugin upgrade, and invisible to a reviewer. There is no manifest `CAMERA` entry to audit.
- **Recommendation:** Explicitly add `<uses-permission android:name="android.permission.CAMERA"/>` (and consider `tools:node`/`maxSdkVersion` guidance) to the main manifest so the requirement is self-documenting and survives plugin changes. Confirm the merged manifest in a release build contains `CAMERA`.

### SEC-03 — ML Kit uses a raw `file://` URI — P1
- **File:** `android/app/src/main/kotlin/app/jws/tallybowl/MainActivity.kt`
- **Evidence:**
  ```kotlin
  val source = File.createTempFile("tallybowl-ocr-", ".jpg", cacheDir)
  source.writeBytes(bytes)
  val image = InputImage.fromFilePath(this, Uri.fromFile(source))
  ```
- **Impact:** `Uri.fromFile` produces a `file://` URI. ML Kit's `fromFilePath` may read via `ContentResolver`, and on Android 7+ (API 24) `file://` URIs are subject to `FileUriExposedException` under StrictMode/context. This is exactly the kind of path the docs list as "compile-verified, runtime untested." It may work on some devices and crash on others.
- **Recommendation:** Either (a) write the temp file and pass a `FileProvider.getUriForFile(...)` content URI (add a `FileProvider` to the manifest), or (b) avoid the temp file entirely by constructing `InputImage.fromByteBuffer` with the correct width/height/rotation metadata (at the cost of manual EXIF handling). Confirm with a physical-device test.

### SEC-04 — Data at rest is unencrypted — P2
- **Files:** `lib/src/data/bowl_store.dart`, `lib/src/data/exports.dart` (`before-restore.json`, backup JSON).
- **Impact:** SQLite journal, backup files, and the recovery copy are plaintext in the app sandbox/`Application Support`. This is acceptable for a local-only journal and is documented, but it is a privacy consideration (bowler names, aliases, notes, locations).
- **Recommendation:** Keep as-is for now, but document the decision and consider SQLCipher / encrypted backup if the app ever stores more sensitive data or syncs. Do not silently change without a migration story.

### SEC-05 — Hardcoded User-Agent version — P3
- **File:** `lib/src/config.dart`
- **Evidence:** `static const userAgent = 'TallyBowl/0.1.1 (+https://tallybowl.jws.app)';`
- **Impact:** On every version bump the UA will drift from the actual version. Tile/Photon providers use this to identify the client; a stale version is misleading.
- **Recommendation:** Derive the version from the app's package info (`package_info_plus`) or at minimum update it as part of the release checklist.

## 4. Compatibility

### COM-01 — Android physical-device flows untested — P1
- **Files:** `lib/src/recognition/photo_service.dart`, `android/.../MainActivity.kt`, `docs/DEVELOPMENT.md`.
- **Impact:** `docs/DEVELOPMENT.md` states Android recognition is "compile-verified, with runtime device checks still outstanding," and physical camera/permission/share/interrupt flows are untested on Android, iPad, and Mac. A successful build is not evidence these work.
- **Recommendation:** Before release, run the camera → OCR → review → save → share loop on real Android and iPad devices; test Android process-death recovery (`retrieveLostData`), interrupted picking, and the share sheet.

### COM-02 — macOS signing/hardened-runtime/notarization not configured — P1
- **Files:** `macos/Runner.xcodeproj/project.pbxproj`, `macos/Runner/Release.entitlements`, `docs/DEVELOPMENT.md`.
- **Evidence:** `CODE_SIGN_STYLE = Manual`/`Automatic` entries exist but there is no distribution team/provisioning, and `ENABLE_HARDENED_RUNTIME` was not found in the build settings. The release entitlements correctly omit debug-only keys, but no notarization setup is present.
- **Impact:** The macOS app will be blocked by Gatekeeper or rejected for distribution without hardened runtime + notarization (or App Store signing).
- **Recommendation:** Enable hardened runtime, configure Developer ID / App Store signing, and add notarization to the release pipeline.

### COM-03 — Production map tile & place-search hosts not selected — P1
- **File:** `lib/src/config.dart`, `docs/DATA_SOURCES.md`, `docs/DEVELOPMENT.md`.
- **Evidence:** Defaults are `https://tile.openstreetmap.org/{z}/{x}/{y}.png` and `https://photon.komoot.io/api/` (public demo services). `docs/DATA_SOURCES.md` explicitly says no production capacity is reserved and policies may throttle/ban.
- **Impact:** At scale the app could be throttled/banned; attribution/usage requirements differ per provider.
- **Recommendation:** Choose a hosted/self-hosted OSM-compatible tile provider and a Photon instance appropriate to traffic, then override via the existing `TALLYBOWL_TILE_URL` / `TALLYBOWL_PHOTON_URL` dart-defines and update attribution.

### COM-04 — `DropdownButtonFormField.initialValue` semantics — P2
- **Files:** `lib/src/features/game_editor.dart`, `lib/src/ui/dialogs.dart` (`startSession`).
- **Evidence:** Both dropdowns are declared with `initialValue:` rather than a controlled `value:`. In `game_editor.dart` the primary-ball dropdown also uses `key: ValueKey(_primary)` to force recreation.
- **Impact:** `initialValue` is valid in the pinned Flutter (3.47.5) so this is not an analyze error, but the behavior is the newer "initial value" semantics, and the `key:`-recreation pattern is fragile. Verify that selected values always visually update on all three platforms; if not, switch to the controlled form.
- **Recommendation:** Use the controlled `value:`/`onChanged` form (or confirm `initialValue` + `didChange` behavior) and remove the `ValueKey` recreation workaround.

### COM-05 — `dart:io` / `Platform` branching assumes exactly three targets — P2
- **Files:** `lib/src/data/exports.dart` (`Platform.isMacOS`), `lib/src/recognition/photo_service.dart` (`Platform.isMacOS`, `Platform.isAndroid`), `lib/src/ui/score_photo_preview.dart` (`Image.file`).
- **Impact:** This is fine for the three target platforms, but it means any future web/Windows/Linux target will silently misbehave (e.g., fall through to the share-sheet path). Not a current defect, but a latent trap.
- **Recommendation:** Centralize platform capability checks (e.g., a small `PlatformSupport` abstraction) if other targets are ever added.

### COM-06 — Recent-API usage pins minimum Flutter — P3
- **Files:** `lib/src/ui/common.dart` (`Color.withValues(alpha:)`), `lib/src/features/session_share.dart` (`ShareParams.fileNameOverrides`), `lib/src/app.dart` (`onPopInvokedWithResult`).
- **Impact:** Requires a recent Flutter SDK (the project pins 3.47.5/Dart 3.13.4). Fine now, but contributors with older SDKs will hit build errors.
- **Recommendation:** Document the minimum Flutter version in `README.md`/`DEVELOPMENT.md` and consider a CI matrix pin.

### COM-07 — iPad-only device family — P3
- **File:** `ios/Runner.xcodeproj/project.pbxproj` (`TARGETED_DEVICE_FAMILY = 2`).
- **Impact:** The iOS build is iPad-only (intended per README), but it will not run on iPhone. Confirm this is intentional (it matches the stated iPadOS target).
- **Recommendation:** Keep as-is if iPad-only is intended; otherwise set `TARGETED_DEVICE_FAMILY = 1,2` and test phone layouts.

## 5. Accessibility

### A11Y-01 — Light-only theme (no dark mode) — P2
- **File:** `lib/src/theme.dart`.
- **Evidence:** A single `ThemeData` is always used; there is no `darkTheme:`/`themeMode:` and no `ColorScheme` for dark surfaces.
- **Impact:** Users who rely on dark mode (and macOS/iPadOS system dark appearance) get a forced light UI.
- **Recommendation:** Add a dark `ThemeData` and respect `MediaQuery.platformBrightnessOf` (optionally a settings toggle).

### A11Y-02 — Hardcoded tiny font sizes don't scale — P2
- **Files:** `lib/src/app.dart` (font sizes 8/10/11), `lib/src/ui/common.dart` (11/12), and many others.
- **Evidence:** Many `TextStyle(fontSize: ...)` literals are fixed; the app does not use `MediaQuery.textScalerOf` or a scaled text theme.
- **Impact:** With iPadOS/macOS "Larger Text" accessibility settings, these labels do not grow and can become illegible.
- **Recommendation:** Run the app at 1.5×–2× text scale, replace fixed decorative sizes with scaled theme typography, and verify no overflow in `Wrap`/`FittedBox`/`SingleChildScrollView`.

### A11Y-03 — No accessibility testing and decorative non-semantic elements — P2
- **Files:** `lib/src/features/insights.dart` (chart), `lib/src/ui/common.dart` (`BallArt`), `lib/src/features/journal.dart` (hero).
- **Impact:** The insights bar chart, ball artwork, and gradient hero are visual-only. Screen readers will not announce meaningful equivalents for the chart, and the hero text may not be reachable in a logical order.
- **Recommendation:** Add semantic labels to the chart (already partially present via `Semantics(label: ...)`) and mark decorative artwork with `ExcludeSemantics`. Run iOS VoiceOver and Android TalkBack smoke tests.

### A11Y-04 — `ScoreStrip` and `BallArt` lack semantics — P3
- **Files:** `lib/src/ui/common.dart` (`ScoreStrip`, `BallArt`).
- **Impact:** The frame grid reads as disjoint text nodes; screen-reader users cannot reconstruct the scorecard.
- **Recommendation:** Wrap `ScoreStrip` in a single `Semantics` describing the ten frames/notation/cumulative scores, and give `BallArt` a semantic label or exclude it.

### A11Y-05 — Contrast on gradient hero and muted text — P3
- **Files:** `lib/src/features/journal.dart`, `lib/src/theme.dart` (`BowlColors.muted = Color(0xFF607274)`).
- **Impact:** Light text (`Color(0xFFD6E3DB)`, `Color(0xFFC5DDCC)`) on the dark gradient, and muted gray on white, may fall short of WCAG AA contrast.
- **Recommendation:** Audit contrast ratios and darken/lighten as needed; verify with a contrast checker.

## 6. Cohesiveness

### COH-01 — "Save image" shares instead of saving on iPad/Android — P2
- **Files:** `lib/src/features/session_share.dart` (`_export`), `lib/src/data/exports.dart` (`exportFile`).
- **Evidence:** `exportFile` uses `getSaveLocation` only on macOS; on iPad/Android both "Share image" and "Save image" go through `SharePlus` (share sheet).
- **Impact:** A "Save image" button that opens a share sheet is inconsistent with the label and does not persist to Photos.
- **Recommendation:** On iPad/Android, write the PNG to the photo library (requires `NSPhotoLibraryAddUsageDescription` on iOS) or clearly relabel the action to "Export image".

### COH-02 — Mobile `NavigationBar` used in narrow macOS windows — P2
- **File:** `lib/src/app.dart` (breakpoint `wide = constraints.maxWidth >= 850`).
- **Impact:** On a narrow macOS window (< 850 px) the app falls back to a bottom mobile tab bar, which is atypical on desktop. It also hides the always-visible Settings affordance.
- **Recommendation:** Keep the sidebar/AppBar for macOS at all window sizes (or use a macOS-appropriate navigation rail), and reserve the bottom `NavigationBar` for touch devices.

### COH-03 — Scattered magic breakpoint numbers — P3
- **Files:** `lib/src/app.dart` (850), `lib/src/ui/common.dart` (800/420), `lib/src/features/*` (700/430/750/1000/580).
- **Impact:** The responsive thresholds are inconsistent and hard to audit as a set; minor width differences can produce different column counts on similar screens.
- **Recommendation:** Introduce shared breakpoint constants and a single "content max width" policy.

### COH-04 — Dropdown recreation via `ValueKey` — P3
- **File:** `lib/src/features/game_editor.dart`.
- **Evidence:** `DropdownButtonFormField<String>(key: ValueKey(_primary), initialValue: _primary ?? '', ...)`.
- **Impact:** Forcing a new element identity to reset the field works but discards form state and is a code smell; it will also interfere with any future `Form` validation integration.
- **Recommendation:** Replace with a controlled dropdown (see COM-04) and remove the `key`.

### COH-05 — `message()` after `Navigator.pop()` — P3
- **File:** `lib/src/features/game_editor.dart` (`_save`).
- **Evidence:**
  ```dart
  Navigator.pop(context);
  message(context, 'Game saved · ${result.total}');
  ```
- **Impact:** Using a route's `context` immediately after popping it is fragile (the route is being disposed during the pop animation). It currently finds the root `ScaffoldMessenger`, but it can throw or attach to the wrong messenger if the structure changes.
- **Recommendation:** Show the snackbar before popping, or capture `ScaffoldMessenger.of(context)` (or use a root messenger key) before the pop.

## 7. Maintainability

### MNT-01 — Native code excluded from static analysis — P2
- **File:** `analysis_options.yaml` (`analyzer.exclude: android/**, ios/**, macos/**`).
- **Impact:** Swift/Kotlin/native configuration issues (like SEC-02/SEC-03) are invisible to `flutter analyze`. The project relies on manual review of the native layer.
- **Recommendation:** Add a separate native lint (SwiftLint for iOS/macOS, ktlint/detekt for Android) in CI, or at minimum review native diffs explicitly.

### MNT-02 — Very large feature files — P3
- **Files:** `lib/src/features/game_editor.dart` (503 lines), `lib/src/features/journal.dart` (636 lines).
- **Impact:** These files mix layout, state, and navigation; they are harder to test and review.
- **Recommendation:** Extract reusable widgets (game card/session card already exist; extract the editor's scoring header, frame grid, and ball-tagging sections).

### MNT-03 — Place-search cache eviction relies on map order — P3
- **File:** `lib/src/data/place_search.dart`.
- **Evidence:** `if (_cache.length >= 30) _cache.remove(_cache.keys.first);`
- **Impact:** Correct only because the default `{}` map is a `LinkedHashMap` with insertion order. A future refactor to another map type would silently evict the wrong entry.
- **Recommendation:** Track insertion order explicitly or use an LRU-friendly structure.

### MNT-04 — Test coverage gaps — P3
- **Files:** `test/`, `integration_test/`, `docs/DEVELOPMENT.md`.
- **Impact:** 41 unit/widget tests cover scoring/persistence/parser/exports, but there are no golden tests for the recap/visuals, no accessibility tests, and no large-history performance benchmarks (docs flag snapshot serialization as O(journal size)).
- **Recommendation:** Add widget golden tests for key screens, a large-history performance test, and a device matrix test for the native camera/OCR/share path.

### MNT-05 — Manual catalog sync burden — P3
- **Files:** `lib/src/data/ball_catalog.dart`, `docs/DATA_SOURCES.md`.
- **Impact:** The brand/model starter list is hand-maintained and the docs require keeping it in sync with verified first-party sources.
- **Recommendation:** Accept for now, but document the list's source/date and add a test that asserts the list is non-empty and deduplicated (so regressions are caught).

## 9. Verification of findings (second pass)

A second pass re-checked every finding against the actual source. Confirmed as written:

- SEC-01: `signingConfig = signingConfigs.getByName("debug")` present in `android/app/build.gradle.kts`.
- SEC-02: main `AndroidManifest.xml` declares only `INTERNET`; camera is used via `image_picker`.
- SEC-03: `InputImage.fromFilePath(this, Uri.fromFile(source))` present in `MainActivity.kt`.
- SEC-04/SEC-05: plaintext SQLite/backup and hardcoded UA confirmed in `bowl_store.dart`/`exports.dart`/`config.dart`.
- COM-01: explicitly stated in `docs/DEVELOPMENT.md`; Android recognition compile-only.
- COM-02: no `ENABLE_HARDENED_RUNTIME` found in `macos/Runner.xcodeproj/project.pbxproj`; distribution signing not configured.
- COM-03: dev defaults in `lib/src/config.dart`; capacity/policy caveats in `docs/DATA_SOURCES.md`.
- COM-04/COH-04: `initialValue` + `ValueKey` pattern confirmed in `game_editor.dart` and `dialogs.dart`.
- COM-05/COM-06/COM-07: `dart:io`/`Platform` usage, `withValues`, and `TARGETED_DEVICE_FAMILY = 2` all confirmed.
- A11Y-01…A11Y-05: single light theme, fixed font sizes, and visual-only widgets confirmed.
- COH-01…COH-05: `exportFile` platform branching, 850 breakpoint, magic numbers, `ValueKey`, and post-pop `message()` all confirmed.
- MNT-01…MNT-05: analyzer excludes native dirs; large files; `_cache.keys.first`; test/bench gaps; manual catalog all confirmed.

No finding was found to be inaccurate during verification. The two items that depended on environment behavior rather than static code — `DropdownButtonFormField.initialValue` semantics (COM-04) and `Uri.fromFile` with ML Kit (SEC-03) — are flagged as "verify on device/compile" rather than asserted as definite crashes.
